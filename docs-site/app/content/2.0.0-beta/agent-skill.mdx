## Installation

```bash
npx @grampro/kit skill
```

The block writes the skill at the root of the project you run it in — not into `component-lib/` — in the place each supported agent looks. Commit the result so that everyone on the team, and CI, gets the same guidance.

`-a -skill` and `-a skill` do the same thing, and it can be combined with a component install:

```bash
npx @grampro/kit add DataGrid -skill
```

An agent that has never seen this library will otherwise guess. It will write `import { Button } from "@grampro/kit"`, which does not resolve, because the CLI copies source into your repo rather than publishing a package to import from. It will reach for `onChange` on a `Switch`, which the type omits. It will wrap an `Input` in its own `<label>` and break the wiring the component already does. The skill is the file that stops all three.

<Notice message="This is not documentation for people — it is a file your coding agent reads. It is written as rules rather than prose, and it is deliberately short, because the part that is always in the agent's context has a budget measured in characters." />

## What lands in your repo

```
.gbs/                                canonical, and what the GBS agent reads
  .install-manifest.json
  skills/gbs-components/
    SKILL.md                         always in the agent's context
    references/
      install.md                     CLI flags, folder names, shared/
      forms.md                       text and choice fields
      pickers.md                     Select, MultiSelect, DatePicker, FileUploader
      overlays.md                    Modal, dialog, Popover, Menu, Tooltip
      toaster.md                     toast() and Toaster
      data-grid.md                   columns, imperative API, export
      data-display.md                Card, Tabs, Accordion, Badge, Avatar, Progress
      styling.md                     --gbs-* tokens, layers, slots, data-*
      accessibility.md               what is supplied, what you must add

.claude/skills/gbs-components/       Claude Code
.agents/rules/gbs-components.md      Antigravity
AGENTS.md                            Codex — a marked block, nothing else touched
```

Only `SKILL.md` is loaded up front. It is an index: the import rule, the handful of rules that are most often got wrong, a one-line inventory of every component, one complete example, and a list of things not to do. The agent opens a reference file only when the task needs that depth, so a small change does not drag eleven thousand characters of DataGrid documentation into the conversation.

## What it teaches

The rules that earn their place are the ones a reasonable agent gets wrong by default.

**Imports.** That there is no package to import from; that components come from `component-lib/<folder>` plus that folder's `styles.css`; that the folder is the lowercased name except for `data-grid`, `date-picker`, `file-uploader`, `number-input` and `radio-group`; and that anything deeper than the barrel is internal.

**Change handler names.** This is the single most common mistake, because nothing in the naming predicts which one a component uses:

| Handler           | Components                                                                                         |
| ----------------- | -------------------------------------------------------------------------------------------------- |
| `onValueChange`   | Input, OtpInput, Textarea, NumberInput, CheckboxGroup, RadioGroup, Tabs, Accordion, MenuRadioGroup |
| `onCheckedChange` | Checkbox, Switch, MenuCheckboxItem                                                                 |
| `onChange`        | Select, MultiSelect, DatePicker, DateRangePicker, FileUploader                                     |
| `onOpenChange`    | Modal, Popover, Menu                                                                               |

**Fields own their own markup.** `label`, `description` and `error` are props. `error` also sets `aria-invalid` and appends the message to `aria-describedby`. An agent that hand-rolls a `<label htmlFor>` around the control is fighting wiring that is already there.

**Styling goes through the library's seams** — `--gbs-*` on `:root` for the palette, `classNames` slot maps for inner parts, `data-*` attributes for state — rather than `!important` or selectors written against internal class names.

**The two things that must be mounted once:** `<Toaster />` and `<DialogHost />`. Without them `toast()` and `dialog.confirm()` do nothing, silently.

**Composition rules**, such as `Tab` and `TabPanel` throwing outside `<Tabs>`, `AccordionItem` outside `<Accordion>`, and `MenuItem` outside `<Menu>`.

## Keeping it current

Re-run the same command to update:

```bash
npx @grampro/kit skill
```

The installer records a sha256 of every file it writes — across all four locations — in `.gbs/.install-manifest.json`. On the next run it compares, and it will not replace a file you have edited:

```
✗ These skill files have local changes:
  - .claude/skills/gbs-components/references/forms.md

  Updating the skill would replace them. Re-run with --force to do that,
  or move your own guidance into a separate skill folder first.
```

`--force` overwrites anyway. Files an older version installed and that you have not touched are cleaned up on update.

<Notice message="Put your own house rules in a separate folder, such as .gbs/skills/our-conventions/, rather than editing this one. The installer merges into .gbs/ and leaves folders it did not write alone, so your skills and this one update independently." />

## An MCP server, for agents that speak it

<Notice message="Beta. The tools work and are tested, but their names and shapes may change before this settles." />

The skill is a document an agent reads up front. The MCP server is the same
catalogue answered on demand, which matters because the passports come to
280 KB and a page needs two or three components.

```bash
npx @grampro/kit mcp install
```

That writes the configuration for every agent it knows — Claude Code, Codex
and Cursor — and names the files it touched. Narrow it with `--for codex`,
or a comma-separated list.

| agent | file | key |
| --- | --- | --- |
| Claude Code | `.mcp.json` | `mcpServers.grampro` |
| Codex | `.codex/config.toml` | `[mcp_servers.grampro]` |
| Cursor | `.cursor/mcp.json` | `mcpServers.grampro` |

Use it rather than editing those files by hand. It writes UTF-8 without a
byte-order mark and with LF endings, and a BOM is the one thing that
reliably breaks them: PowerShell's `Out-File -Encoding utf8` adds one, and
JSON parsers then reject the file with an error that names the first
character and explains nothing. Running it again merges, leaves other
servers alone, and reports `unchanged` when there is nothing to do.

The Codex config is project-scoped. For every project, put the same
`[mcp_servers.grampro]` block in `~/.codex/config.toml`.

An MCP server is not invoked by name. There is no `/grampro`; the model
calls the tools itself when they are relevant. `/mcp` shows whether the
server is connected.

It writes to the project root - the nearest folder above you holding a
`.git` or a `package.json` - and prints which one it picked, because an
agent only reads these files from the folder it has open.

### If the server does not show up

Writing the file is not the same as loading the server, and in Claude Code
two things sit between them.

**It needs approving.** A `.mcp.json` server is project-scoped, and Claude
Code asks before trusting one. Until you agree it stays at `Pending
approval`, and nothing asks a second time; `claude mcp reset-project-choices`
brings the prompt back.

**It needs a fresh session.** The configuration is read at session start, so
an editor window that was already open sees nothing. In the VS Code
extension, run *Developer: Reload Window*.

`/mcp` lists the servers with their state, which separates "not configured"
from "configured, not approved".

Both are skippable by installing it for yourself instead of for the project:

```bash
claude mcp add -s user grampro -- npx -y @grampro/kit mcp
```

User scope lives in `~/.claude.json`, loads in every project, and needs no
approval because it belongs to you rather than to the repository. Project
scope is still the better choice when the team should get it from a commit.

### The tools

| tool | what it answers |
| --- | --- |
| `list_components` | What exists, and what each one is for |
| `get_component` | Props with types and allowed values, which are required, handler signatures, slots, states, composition rules |
| `get_example` | Working usage from the component's README |
| `get_guidance` | Authored notes on forms, overlays, the grid, pickers, styling, accessibility |
| `figma_frame` | A design's structure, text, repeated regions, and the theme variables its colours map onto |
| `install_component` | Copies components into the project being worked in |
| `validate_usage` | Whether the JSX an agent just wrote matches the passports |

`validate_usage` is the point. A page written from passports alone compiles
on the first attempt — every type, union value and handler signature in a
passport is accurate, because it was generated from the source. What a
passport cannot stop is a model reaching for a prop it remembers from
somewhere else, so the server checks:

```
<Alert variant="info" title="Hi" dismissible onDismiss={...} />

  dismissible - not a prop of this component. Did you mean: onDismiss
```

It starts in about the time an empty Node process takes. An agent spawns the
server once per session, so the `mcp` command is routed before the CLI's own
dependencies load; they are no use to a JSON-RPC loop and cost around 70ms.

### Building from a Figma design

Two routes, and the second needs no credentials.

**By URL** - pass a `figma.com/design/...` link. With just the URL it lists
the frames in the file; called again with a `frame` it returns that screen.
A link that already carries a `node-id`, which is what Figma copies when you
right-click a frame, goes straight there in one call. This route needs a
token.

**By plugin export** - in Figma, run **Grampro Kit -> Export selection for an
agent** and hand the JSON over as `design`. The plugin reads the scene graph
from inside Figma, so it works on any file you can open, asks for nothing,
and cannot be rate limited.

Either way you get the same answer: the structure, the text, the regions
whose names repeat - eight `Status cell` nodes are a column - and the
`--gbs-*` variables the design's own colours and radii map onto.

It does not decide which component each region is. A design drawn without
the component library has no instances to look up, so that call is
inference, and an agent holding the catalogue and the designer's own names
for things infers better than string matching inside a tool would. Anything
that is not a kit component is reported as such rather than approximated.

Colours are given roles rather than ranked, because the most-used colour in
a design is the body text and a near-black navy scores high on saturation -
so "most common" and "most saturated" both pick the wrong one. Lightness and
saturation together find the accent.

### Rate limits

Figma charges for file reads by the size of the response, so asking for a
whole file to answer a question about one frame is what earns a 429 - and
the lockout is long. A `Retry-After` of 395274 has been seen on one token.

Nothing here fetches a whole file any more. The frame listing uses
`depth=1`, which returns the document's outline rather than its contents,
and the frame itself is fetched by id. Responses are held for five minutes,
so the natural flow of list-then-read costs one outline and one frame. A URL
with a `node-id` skips the listing entirely.

If a token is already locked out, the plugin export still works.

### Credentials

The URL route needs a Figma personal access token, and it goes where the
operating system keeps credentials:

```bash
npx @grampro/kit secret set figma
```

It prompts with the echo off and never takes the value as an argument -
arguments land in shell history and in every process listing on the machine.
For a script, pipe it: `echo "$TOKEN" | npx @grampro/kit secret set figma`.

| platform | where it goes |
| --- | --- |
| Windows | Data Protection API, tied to your Windows account |
| macOS | the keychain |
| Linux | Secret Service (GNOME Keyring, KWallet) |
| anything else | a 0600 file in your config directory, and it says so |

`secret list` shows what is stored, masked, and names the backend in use;
`secret remove figma` deletes it. Give the token `File content: read` and
nothing else.

The lookup order is `FIGMA_TOKEN` in the environment, then the store, then a
`.env` - the last only so an upgrade does not break a project set up the old
way, and it prints a note saying to move it. A credential in a file inside a
working tree is one `git add -A` away from being published, which is why
this moved.

## Which agents read it

No agent reads all of these locations, so the CLI writes one copy per agent from the same source. They differ only in where they sit and what their front matter is called.

| Agent        | Location                          | Attaches by                                        |
| ------------ | --------------------------------- | -------------------------------------------------- |
| GBS SE Agent | `.gbs/skills/gbs-components/`     | `autoAttach` globs                                 |
| Claude Code  | `.claude/skills/gbs-components/`  | `description`, plus `paths` globs                  |
| Antigravity  | `.agents/rules/gbs-components.md` | a glob set on the rule in the IDE                  |
| Codex        | a block in `AGENTS.md`            | always in context (it is a pointer, not the skill) |

Narrow it if you only use some:

```bash
npx @grampro/kit skill --for claude,codex
npx @grampro/kit skill --for none          # only .gbs/
```

Dropping a target on a later run removes the files it wrote, and empty folders with them. A `.claude` folder that also holds your own settings is left in place.

<Notice message="Antigravity sets a rule's glob on the rule itself rather than in the file, so the generated rule states the globs in its first lines for whoever configures it. Claude Code and the GBS agent both pick their globs up from the file." />

The `description` is the only part always in an agent's context, and for Claude Code it is the main thing that decides whether the skill loads at all. If an agent is not picking the skill up on UI work, that line is what to look at first.

## Codex and AGENTS.md

`AGENTS.md` is always in context and usually maintained by hand, so the skill is not inlined there — 5 KB in every conversation is a poor trade. Instead the CLI writes a pointer inside markers:

```md
<!-- @grampro/kit:start -->

...

<!-- @grampro/kit:end -->
```

Anything outside those markers is never touched. If the file does not exist it is created; if the block is already there it is replaced in place; if the file exists without the block it is appended. This is also the one part not covered by the edit check, because the project owns the rest of the file.

Codex also speaks MCP, and the server is the better of the two routes for it: the pointer in `AGENTS.md` tells Codex the catalogue exists, while `npx @grampro/kit mcp install --for codex` lets it ask. Both can be in place at once, and the pointer costs a few lines rather than 5 KB.
